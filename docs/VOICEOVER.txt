PROPERTYFLOW WALKTHROUGH — VOICEOVER DRAFT

Opening — observed problem and expected results
Here is my investigation and fix for the existing PropertyFlow dashboard. Both supplied accounts returned the same one-thousand-dollar total and three bookings. That came from fabricated fallback data. Property IDs are reused across tenants: Sunset's Beach House Alpha should report two thousand two hundred and fifty dollars and four March bookings. Ocean's separate property has no seeded bookings and should report zero. I kept the existing architecture and sample data.

Tenant cache — original code and fix
The original Redis key used only the property ID. That allowed a response cached for one company to be returned to another company with the same property ID. The fixed key includes the tenant, property, month, and year. A new versioned namespace avoids reusing already polluted entries. The service also checks the identity and structure of cached data. Every database query uses both tenant and property ID. Cache failures read the actual database; they do not produce invented financial results.

Live demonstration — both accounts and refresh
Here is Sunset's account with March selected. The correct result is two thousand two hundred and fifty dollars and four bookings, and its selector shows only Sunset's properties. After signing out and signing in as Ocean, property zero zero one is Mountain Lodge Beta. It correctly returns zero and no bookings. Refreshing and selecting that property again produces the same result. Sunset's property names and revenue are absent from this account.

Time zones — source data and boundaries
The month-boundary reservation checks in on February twenty-ninth at twenty-three thirty UTC. In Paris, that is March first at thirty minutes past midnight. Its twelve hundred and fifty dollars therefore belongs in March. The fix constructs calendar boundaries in the property's time zone, converts them to aware UTC instants, and uses an inclusive start with an exclusive end. Paris changes offset during March, so the end boundary is twenty-two hundred UTC. The tests also cover New York, daylight-saving changes, leap years, and December rollover.

Live demonstration — February, March, and the full year
Back in Sunset's account, selecting February correctly shows zero. Restoring March includes the local March booking and returns two thousand two hundred and fifty dollars. The full-year option uses the same calculation with annual local-calendar boundaries. There is no separate placeholder or hard-coded monthly result.

Money — exact sums and one rounding step
The seed amounts are three hundred and thirty-three point three three three, the same amount again, and three hundred and thirty-three point three three four. They sum to exactly one thousand. Rounding each booking first would lose a cent. PostgreSQL sums the original NUMERIC values, Python keeps Decimal arithmetic and rounds once with round half up, and the API sends a fixed decimal string. The frontend formats that string without converting it to a floating-point number. A half-cent regression verifies the rounding rule. Mixed currencies are rejected rather than silently combined or labeled as US dollars.

Database pool — the hidden source of fabricated totals
The original pool built its URL from legacy settings that are not present in this challenge, used the wrong pool class for asynchronous SQLAlchemy, and exposed the session incorrectly. The revenue service caught failures and returned hard-coded totals, making broken database access look like success. The repaired shared pool uses DATABASE_URL, SQLAlchemy's asynchronous pooling, and the correct session lifecycle. Fabricated revenue is removed. A database failure returns service unavailable; a Redis failure still calculates from PostgreSQL.

Authentication and UI follow-through
The dashboard takes its tenant from verified authentication and fails closed when it is missing. A property belonging to another tenant receives the same not-found response as an unknown property. I also removed the unsigned-token fallback, bounded cached authentication by token expiry, and corrected password validation outside the two challenge fixtures. The property selector now comes from a tenant-scoped endpoint. Account or selection changes discard stale responses. Browser testing also exposed and fixed mismatched local-session response shapes. The invented growth percentage is gone.

Verification and close
There are forty-three passing regression tests locally and in GitHub Actions on PostgreSQL fifteen. Coverage includes both tenant cache orders, exact money, time-zone boundaries, invalid authentication, foreign properties, mixed currencies, and outage behavior. The production frontend build passes. Both provided accounts were tested in the browser, including refresh and an intentionally delayed old response. The final browser session has no console errors.
